# 冲突解析模块

`conflicts` 只读代码和索引，在 Git 私有目录 `git-helper-backups/<唯一编号>/` 保存 HEAD、索引冲突条目、工作区原始字节和 stage 1/2/3 blob，不修改代码或暂存。快照可能含敏感信息，不能上传；它仅覆盖冲突路径，不是完整仓库备份。

## 展示与选择

逐文件展示完整冲突代码、base、ours、theirs，说明 base 是共同祖先。普通 merge 的 ours 为当前分支，theirs 为待合并分支；rebase 的 ours 通常为重放目标，theirs 为被重放提交，必须先确认上下文。

提供选项，并展示每个方案拟写入的具体代码及可能丢失的逻辑：

1. 保留当前侧，说明舍弃的传入改动。
2. 保留传入侧，说明舍弃的当前改动。
3. 人工组合，展示完整候选并解释接口兼容性和重复逻辑。
4. 暂不处理，保留现场。

二进制只显示长度与 blob ID，不解码后写回；删除/修改、重命名、符号链接、子模块冲突需逐路径拟定方案，不能套用文本拼接。

## 示例：超时时间与重试次数发生普通 merge 冲突

以下 `src/request_options.py` 是演示文件，并非本项目已有业务代码。假设用户在当前 `feature/long-timeout` 分支执行普通 merge，合入另一分支 `feature/retry`，双方修改了同一行配置。`timeout` 单位为秒，`retries` 表示首次请求失败后允许追加的尝试次数；示例只构建配置，不实现请求或重试。

共同祖先（stage 1 / base）：

```python
def request_options():
    return {"timeout": 10, "retries": 0}
```

当前侧（stage 2 / ours）把超时时间从 10 秒延长为 30 秒；传入侧（stage 3 / theirs）保留 10 秒超时，增加 2 次重试。`conflicts` 会展示工作区冲突内容以及三个 stage 版本，并输出快照位置。工作区冲突段如下（为避免本项目提交检查把文档当成未解决冲突，展示内容额外缩进四个空格）：

```text
    def request_options():
    <<<<<<< HEAD
        return {"timeout": 30, "retries": 0}
    =======
        return {"timeout": 10, "retries": 2}
    >>>>>>> feature/retry
```

Codex 应先说明：这是同一行配置的冲突，双方意图分别是延长等待时间和增加重试；下面是候选方案，尚未写入任何内容。

### 方案 A：保留当前侧

拟写入 `src/request_options.py` 的完整代码：

```python
def request_options():
    return {"timeout": 30, "retries": 0}
```

保留 30 秒超时，舍弃传入侧新增的 2 次重试；依赖该配置的调用方仍然不重试。适用于用户希望延长单次等待、暂不引入重试的情况。

### 方案 B：保留传入侧

拟写入文件的完整代码：

```python
def request_options():
    return {"timeout": 10, "retries": 2}
```

保留 2 次重试，舍弃当前侧延长至 30 秒的改动；每次请求仍使用 10 秒超时。原本需要等待更久的请求可能更早超时，重试是否合适取决于请求是否允许重复执行。

### 方案 C：人工组合双方意图

拟写入文件的完整代码：

```python
def request_options():
    return {"timeout": 30, "retries": 2}
```

保留双方新增的配置，但不代表自动获得正确行为：若调用方每次尝试都使用 30 秒超时，首次请求加 2 次重试共可尝试 3 次，仅超时等待就可能累计到 90 秒，退避等待等还会增加耗时。应确认总耗时预算，以及请求是否幂等或具有去重机制，不能因为文本可组合就默认选择此项。

### 方案 D：暂不处理

不拟写入替代代码，不暂存，也不继续 merge。保留原有冲突内容、未合并索引和快照；不会丢弃任一侧的版本，但合并仍未完成。可以先确认业务要求再选择其他方案。

### 向用户确认并验证选定方案

展示上述代码和影响后，询问：“请选择 A、B、C 或 D；如果选择 C，请确认 30 秒超时与 2 次重试符合调用方的总耗时和重复执行要求。”在收到选择前停止写入。

例如用户明确选择 C 后，按下一节核对 HEAD、索引和工作区未变化，再仅替换该文件。验证 `request_options()` 返回 `{"timeout": 30, "retries": 2}`，并运行调用方有关超时、重试次数和重复执行的测试；字典断言本身不能证明调用方正确执行了重试。相关测试通过且 diff 与用户选定代码一致后，才暂存该路径。不要把选定冲突方案当成批准提交、推送或合并 PR。

## 用户选定后

1. 重新核对 HEAD、索引 stage/blob、工作区原始字节与快照一致。有变化则重新展示和选择，不能沿用过期决策。
2. 保留快照，只对选定路径写入选定代码；检查实际 diff 与候选一致。删除前备份原始文件，不批量 checkout --ours/--theirs。
3. 检查剩余标记、`git diff --check` 和项目相关测试。成功后 `git add -- <明确路径>`；删除必须用户明确选择后 `git rm -- <路径>`。
4. `git ls-files -u` 确认剩余冲突，审阅暂存 diff。测试失败停止；继续 merge/rebase、提交或推送仍须在用户原任务授权内。

禁止 `reset --hard`、`clean -fd`、强推、自动丢弃工作区。取消 merge/rebase 前，备份操作后新增修改、索引和未跟踪文件，解释 abort 影响并按用户选择执行。
